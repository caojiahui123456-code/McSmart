# 点餐编排剧本

> 记录典型场景（减脂党/预算党/遛娃家庭）的推荐编排路径与回复话术模板。
> 所有数值口径见 `nutrition-rules.md`，工具形态见 `mcp-tools.md`。

## 通用执行顺序（不可颠倒）

1. 先跑 CLI 拿官方方案（`python -m src.main "<用户原话>"`，原话不要改写）
2. **再核对候选池**：CLI 的 `营养达标候选` 数量若 < 3，说明单品硬过滤把组合层可用的
   "半份优质食材"剔除了 → 必须手工在组合层复核一次（见下方陷阱一）
3. 券后价必须走 `calculate-price` 试算，不要用券面标题里的"9.9元"直接当成交价

## 场景 A：减脂 / 轻食晚餐

意图样例："我最近减肥，但是晚上想吃麦当劳，预算50元"

- goal=`减脂`（触发词：减肥/减脂/瘦身/轻食/热量低/低卡）
- 硬约束：单餐 ≤600kcal、蛋白 ≥20g、钠 ≤800mg
- 编排：碳水与甜饮先砍掉；饮品优先 `鲜萃咖啡`(¥9.5, 13kcal) 或 `锡兰红茶`(¥11.5, 2kcal)
- **单品层够不着 20g 蛋白、但组合层能凑够的食材一定要手工补**：
  典型是 `薄皮焦香V翅`(192kcal/P17/F11/Na594, ¥16)，
  与 `玉米杯`(87kcal/P4/F1/Na2, ¥13) 组合后 = 蛋白 21g、脂肪 12g、热量 279kcal，
  比任何单个 ≥20g 蛋白的汉堡（脂肪普遍 21-26g）都更适合减脂。
- 话术：给出"首推轻量组合 / 一个堡搞定 / 吃饱型"三档，明确标注脂肪与钠，不评判用户

## 场景 B：省钱（怎么买最划算）

意图样例："今天吃麦当劳怎么最划算" / "预算50元"

- goal=`省钱`，走 `deal_optimizer` 专用流水线（不做营养筛选）
- 顺序：`query-my-coupons` → `query-store-coupons` → `query-promotions`(按 beType 过滤) → 试算
- 只有 `query-store-coupons` 返回 couponId + 适用 productCode，是唯一能做券后试算的数据源
- 券适用商品以 `products[].productName` 为准，**不要用券标题反推商品名**（易误配）

## 场景 C：遛娃 / 儿童餐

意图样例："带孩子吃麦当劳" / "儿童餐推荐"

- goal=`儿童`：热量 ≤500kcal、钠 ≤600mg、蛋白 ≥10g
- 组合上限同样生效：V翅(594mg) + 麦乐鸡(422mg) = 1016mg 会被正确拒绝
- 话术：钠是首要指标，甜饮只在开心乐园餐里保留

## 场景 D：门店查询

意图样例："附近哪里可以买麦当劳"

- 仅当**没有**健康/省钱目标时才走门店轻链路；"减脂期附近有店吗"仍走推荐链路
- 官方 `query-nearby-stores` 不接受经纬度，城市是唯一可控锚点；
  用户未说城市时必须显式标注"按默认城市「北京」查询"（`city_inferred=True`）

## 实测陷阱（2026-10-10，北京中粮广场店）

1. **单品硬过滤误杀（已确认）**：`filter_candidates` 用 `min_protein=20` 卡单品，
   导致 17g 蛋白的优质低脂食材（薄皮焦香V翅等）进不了候选池，
   组合层因此只能出"单品大堡"这一种解，方案数退化为 1 套。
   缓解：候选数 <3 时手工在组合层补算。
2. **不适用的券会静默算出 ¥0.00**：拿 `9.9元中杯冰美式` 券（适用商品
   `麦咖啡™冰美式中杯`）去试算不含该商品的组合，`calculate-price` 返回
   `final_price=0.00 / original_price=0.00`，不报错。上层必须校验
   `original_price>0` 才采信该价格，否则会把"0元"当成最优方案推荐出去。
3. **门店餐牌价 ≠ 试算原价**：`麦咖啡™美式` 餐牌 ¥11.9，试算原价按 ¥19 计。
   对外报价一律用 `calculate-price` 的 `final_price`，餐牌价只用于预算粗筛。
4. **营养表有、门店无**：160 条营养数据中约 1/4（如"蒜了吧黄油风味薄皮脆汁鸡"）
   并未出现在该门店 129 个在售餐品里，筛选前必须与 `query-meals` 结果交叉。
